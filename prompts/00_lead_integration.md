# Промпт для Лидера — Финальная сборка и сводный отчёт (`reports/00_FINAL_SUMMARY.md`)

Используй этот промпт, когда все 5 программистов отправят свои Pull Request (или ветки `feature/*`) в репозиторий.

---

```text
Ты выступаешь в роли Technical Lead / Интегратора студенческого проекта «Система подсчёта посетителей на компьютерном зрении» (`visitor-counter`).

### 1. Контекст
Программисты завершили свои модули в отдельных ветках (`feature/ml-counter`, `feature/video-processing`, `feature/backend-api`, `feature/frontend-dashboard`, `feature/devops-testing`) и оставили отчёты в `reports/01_ml.md` .. `reports/05_devops_qa.md`.
Твоя задача — собрать всё в единое рабочее приложение, устранить нестыковки на стыках модулей, прогнать реальные тесты на видео и подготовить **итоговый сводный файл `reports/00_FINAL_SUMMARY.md`**, по которому вторая часть команды (девушки) соберёт презентацию для защиты.

### 2. Стартовые шаги
1. Переключись на заранее созданную интеграционную ветку `feature/integration` (`git fetch origin && git checkout feature/integration`), обнови её от актуальной `main`.
2. Изучи `PROJECT_SPEC.md`, `AGENTS.md`, `shared/contracts.py` и все отчёты `reports/01_*.md` .. `reports/05_*.md`.
3. Выполни команду `план` — зафиксируй план сборки в `reports/_wip_lead.md`.
4. Сверь порядок слияния веток в `feature/integration` (рекомендуется: `feature/devops-testing` -> `feature/ml-counter` -> `feature/video-processing` -> `feature/backend-api` -> `feature/frontend-dashboard`), а после проверки открой финальный Pull Request в `main`.

### 3. Что нужно сделать при интеграции
1. **Проверить совместимость и подключить модули:**
   - убедиться, что `backend` использует реальные `video.VideoProcessor` и `ml.VisitorCounter` (а не только mock-режим);
   - убедиться, что FastAPI корректно раздаёт `frontend/index.html` и всю статику (`/css/...`, `/js/...`) на `http://127.0.0.1:8000/`;
   - проверить, что `requirements.txt` и скрипт запуска (`run.bat` / `start.ps1`) реально поднимают всё приложение на этом ПК (и задействуют CUDA, если доступна).
2. **Прогнать тесты и сквозной сценарий:**
   - запустить `pytest`;
   - запустить сервер и проверить в браузере полный путь: загрузка видео -> Старт -> отображение MJPEG-потока с рамками/ID/линией -> обновление счётчиков по WebSocket -> Стоп / Завершение.
3. **Замерить точность (минимум на 3 видео разной сложности через `tests/evaluate_accuracy.py` или реальный прогон):**
   - Видео 1 (простое — люди по одному);
   - Видео 2 (среднее — несколько человек одновременно);
   - Видео 3 (сложное — перекрытия, встречные потоки);
   - зафиксировать факт vs система, % ошибки (формула из `PROJECT_SPEC.md`), FPS и время обработки.
   - **Никогда не придумывай цифры:** пиши строго то, что реально получено при запуске.
4. **Сохранить визуальные материалы для презентации:**
   - положить 2–4 реальных скриншота в `reports/assets/` (главный дашборд, кадр с детекцией и виртуальной линией, пример итоговой статистики).
5. По ходу сборки регулярно фиксируй прогресс командой `чекпоинт` в `reports/_wip_lead.md`.

### 4. Финальный результат (`финал`)
Сформируй единый, понятный не-программистам сводный файл **`reports/00_FINAL_SUMMARY.md`**, где обязательно есть:
1. **Как работает собранная система простыми словами** (поток данных от видеофайла до цифр на экране).
2. **Что реально реализовано в MVP** (подтверждённый список функций без обещаний на будущее).
3. **Как запустить и продемонстрировать на защите** (точные команды).
4. **Таблица реальных результатов тестирования на 3+ видео** (сложность, факт IN/OUT, система IN/OUT, % ошибки, средний FPS, GPU/CPU).
5. **Ссылки на скриншоты в `reports/assets/`**.
6. **Честные ограничения и идеи развития** (что пока не умеет прототип и что можно улучшить дальше — например, RTSP-камеры, разделение сотрудников, аналитика по часам).
```
